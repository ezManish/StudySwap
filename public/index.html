Specification & Constraints

1. Core Invariant

The 4th booking on a 3-place session must always be rejected with HTTP 409 Conflict. Capacity is enforced in SQLite via an atomic BEFORE INSERT trigger.

2. Required Flows

  • GET /sessions: Lists sessions with current occupancy and available places.
  • GET /sessions/:id: Returns session detail with active booking records.
  • POST /bookings: Books a place atomically with { sessionId, alias }.
  • POST /bookings/:id/cancel: Cancels booking and returns seat to pool.

3. The Four Test Cases

  • Case 1 (Overbooking): 4th booking on 3-place session returns 409 Conflict.
  • Case 2 (Invalid Session): Booking non-existent session returns 404 Not Found.
  • Case 3 (Double Booking): An alias cannot book the same session twice (409 Conflict).
  • Case 4 (Restart Persistence): SQLite file backed with WAL mode; data survives process restart.
